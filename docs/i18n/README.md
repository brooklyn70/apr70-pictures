## i18n CMS side

### How locales are configured

`cms/src/locales.ts` is the single source of truth. It lists the five site locales
with their code, label, `htmlLang` and two-letter keycode, and exports
`SITE_LOCALES`, `SITE_LOCALE_CODES`, `DEFAULT_LOCALE`, `isSiteLocale()` and
`htmlLangFor()`. The web app imports the same file through the `site-locales`
tsconfig path alias, the way it imports `payload-types` — so the CMS and the site can
never disagree about what a locale is.

`cms/src/payload.config.ts` builds its `localization` block from that file:

```ts
localization: {
  locales: SITE_LOCALES.map((l) => ({ label: l.label, code: l.code })),
  defaultLocale: DEFAULT_LOCALE,   // 'en'
  fallback: true,
}
```

`fallback: true` means an empty Portuguese value serves the English one, so a
half-translated locale never renders a blank page. Every field marked
`localized: true` gains a row-per-locale companion table in Postgres; a field without
the flag has one value shared by all locales (see `localized-fields.md` for which is
which and why).

**Adding a locale** is: add a row to `SITE_LOCALES`, run
`pnpm -C cms payload migrate:create <name>` (the `_locales` enum gains the code),
review, apply. Every existing localized field then has a new empty tab.

### Enabling a locale for the public site

Translating a locale and publishing it are two different decisions.

Every locale in `locales.ts` always exists in the admin as a tab — a translator can
work in it for weeks. What the public site serves is **Site Settings → Languages →
Public languages** (`SiteSettings.enabledLocales`). Tick a locale there and it becomes
routable; untick it and it does not, while the translation stays safe in the admin.
English cannot be removed: a field validator rejects any value that drops `en`,
because it is both the default locale and the fallback for every other one.

The field is `hasMany` select, `required`, and defaults to `['en']`. The migration
seeds `['en']` into the existing Site Settings row, so nothing has to be picked by
hand on deploy.

### The seed locale flag

`cms/scripts/seed-v9.ts` takes `--locale=<code>`:

```sh
pnpm -C cms seed:v9:dry                      # English, exactly as before
pnpm -C cms seed:v9:apply
pnpm -C cms seed:v9:apply -- --locale=pt     # Portuguese
```

With no flag the locale is `en`, the copy canon is the English directory, and the
behaviour is what it has always been. With `--locale=pt` the script reads
`<COPY_DIR>/pt/` — the per-locale vault canon path ruled in plan §G.1 row 10,
`11.12 V9 Build/02-copy/<locale>/` — and passes `locale: 'pt'` to every
`create` / `update` / `updateGlobal` call, so the copy lands in the Portuguese tab and
touches no English value. An unknown locale code, or a missing copy directory, aborts
the run before it writes anything: seeding English text into a foreign tab silently
would be worse than failing.

Three-layer content law (CLAUDE.md rule 16) still applies per locale — live DB, seed
defaults, and the vault copy canon — so a translated page is only finished when its
copy is canonised under `02-copy/<locale>/`.

### The AI Mark backfill

The site used to decide a frame was AI-generated by matching the English phrase
`/ai[\s-]?generated/i` in the caption printed beside it. That rule dies the first time
a caption is translated, and a disclosure that disappears is a compliance failure, not
a cosmetic one. The flag is now stored on the picture: `Media.aiFrame`, un-localized,
"AI-generated frame (AI Mark)" in the admin sidebar.

`cms/scripts/backfill-ai-mark.ts` reads every caption/credit written next to a media
reference — the twelve v9 section blocks on the five page globals, plus every Project
gallery plate, hero and legacy filmstrip tile — applies the old regex to the English
text, and ticks `aiFrame` on the media it names.

```sh
pnpm -C cms aimark:dry      # lists what it would flag, writes nothing
pnpm -C cms aimark:apply
```

It only ever turns the flag on, so a frame Marco has ticked by hand, or one whose
caption has since been translated, is never un-ticked by a re-run. On the rehearsal
copy of the live database it flagged **39 of 206** media documents; a second run
flagged 0 more. The web side keeps the old regex as a fallback for English captions,
so nothing stamped today stops being stamped tomorrow.

### Migration deploy order

Migrate before starting the new cms — which is what
`~/websites/apr70-website/_deploy/deploy-v10-to-nas.sh` already does: it runs the
compose `migrate` service before bringing the new `cms` container up. No change to the
script is needed.

Order on the NAS:

1. Dump the NAS database (the deploy script's own preflight, and worth keeping).
2. `pnpm -C cms preflight` locally — must exit 0 (CLAUDE.md rule 13).
3. Deploy: migrations run, then the new cms starts.
4. Once, after the first deploy of this change: `pnpm -C cms aimark:apply` against the
   NAS database, to set the stored AI Mark on the existing library.

The i18n migration (`20260907_195421_i18n_localization`) moves every English string
out of its old column and into a `_locales` table **before** dropping that column, and
reverses cleanly. Payload's generator does not write that data move — it was added by
hand and proved against a fresh copy of the live database in both directions with zero
values lost. Do not regenerate this migration without re-reading
`migration-rehearsal-2026-09-07.md` first.
